# RUNBOOK — Polymath OS (hardened)

> Усиленная версия. Принципы: (1) у каждой процедуры есть **предусловия, предпросмотр, проверка результата и план «если процедура сама упала»**; (2) «выполнено» = состояние подтверждено проверкой, а не команда вернула 0; (3) необратимое действие требует явного подтверждения человека; (4) неизвестное состояние — это состояние (`UNKNOWN`), его не «додумывают».

> Команды требуют пробного прогона в тестовом окружении. **[проверить]** = поведение зависит от версии.

---

## 0. Шаблон процедуры

```
ПРЕДУСЛОВИЯ   что должно быть верно до начала (и как проверить)
ПРЕДПРОСМОТР  режим «посмотреть, не меняя» (plan / --dry-run / diff)
ДЕЙСТВИЕ      минимальный шаг; необратимое отмечено ⛔ и требует подтверждения
ПРОВЕРКА      наблюдаемый признак успеха (не «команда завершилась»)
ЕСЛИ УПАЛО    что делать, если сама процедура сорвалась; фиксировать UNKNOWN
СЛЕД          запись: время, кто, что проверено, ссылка на артефакты
```

Это предложение основано на усиленной версии SINGULYAR EIR (`runtime/docs/RUNBOOK_HARDENED.md`), адаптированной под Polymath OS. Каждое «выполнено» должно подтверждаться проверкой состояния — это тот же принцип, что в ядре EIR: адаптер сказал «ок» ≠ результат подтверждён.

## 1. Триаж инцидента (вместо «P0 → откат немедленно»)

1. **Что сломано и у кого?** Есть ли риск потери/порчи данных? Если да — **сначала остановить запись**, затем думать.
2. **Коррелирует ли сбой с релизом** (время, диф, флаги)? Если нет — откат не поможет.
3. **Выбор стратегии:**
   - **откат** (релиз виноват, схема совместима)
   - **fix-forward** (откат невозможен: миграция необратима)
   - **failover** (виновата зависимость)
   - **деградация** (отключить функцию флагом)
4. Решение и обоснование записать **до исполнения** (одна строка).
5. **Проверка** — синтетическая проба ключевого пользовательского пути, не только `/health`.

### Severity (не календарная, а по риску)

- **P0 (Critical):** production down, data loss risk. Остановить запись → думать → откат/fix-forward/failover.
- **P1 (High):** major feature broken. Rollback если не фиксится за 30 мин.
- **P2 (Medium):** minor feature broken, workaround exists. Fix в следующий deploy.
- **P3 (Low):** cosmetic, non-urgent.

## 2. Откат релиза

- **ПРЕДУСЛОВИЯ:** последняя зелёная ревизия определена (`gh release list --limit 5`); миграции схемы по схеме **expand/contract** (старый код работает на новой схеме) — иначе откат кода запрещён, идти fix-forward.
- **ПРЕДПРОСМОТР:** `helm history <release>` / `argocd app history <app>`; сравнить диф ревизий.
- **ДЕЙСТВИЕ:** `helm rollback polymath-os-prod <previous-revision>`. **[проверить]** Argo CD может не допускать rollback при включённой автосинхронизации — временно отключить синхронизацию осознанно и вернуть после.
- **ПРОВЕРКА:** проба ключевого пользовательского пути + метрика ошибок возвращается к фону. Не только `/health`.
- **ЕСЛИ УПАЛО:** зафиксировать UNKNOWN, заморозить деплои, эскалация (§8).
- **СЛЕД:** записать timeline, root cause, action items в GitHub Issue с меткой `incident`.

### Три раздельные цели отката (не одна метрика 60 сек)

| Что | Цель | Способ | Метрика |
|---|---|---|---|
| Откат кода | ≤60 сек | `helm rollback` / `argocd app rollback` | Время выполнения rollback-команды |
| Безопасные миграции | expand/contract, без отката данных | Migrate forward всегда; old code compatible with new schema | Тест: old code читает new schema в CI |
| Восстановление данных | RPO/RTO (см. §10) | Restore-test на чистой машине, quarterly | Время восстановления + окно потери |

## 3. CI красный на main

- **Симптомы:** main красный после merge PR; CI timeout; flaky test.
- **ПРЕДУСЛОВИЯ:** локальная среда актуальна (`chezmoi apply && nix develop`).
- **ДЕЙСТВИЕ:**
  ```bash
  act -W .github/workflows/ci.yml -j ci   # воспроизвести локально
  ```
- **ПРОВЕРКА:** если локально зелёно — проблема среды (кэш/runner image/закреплённые версии). Если локально тоже красно — фикс в коде через PR.
- **Анти-паттерн:** не отключать проверку, чтобы «позеленело»; временное исключение оформляется ADR с датой снятия.
- **СЛЕД:** PR с фиксом + ссылка на issue.

## 4. IaC (OpenTofu)

- **Любое действие** начинается с `tofu plan` и сохранения копии state.
- **`force-unlock`:**
  - **ПРЕДУСЛОВИЯ:** подтверждено, что процесс `apply` не выполняется (проверить владельца блокировки, CI-джобы, локальные процессы).
  - **ДЕЙСТВИЕ:** только с подтверждением человека.
  - **ПРОВЕРКА:** `tofu plan` без неожиданных изменений.
- **`destroy` ⛔:**
  - Только скриптом-обёрткой, которая проверяет имя окружения и требует ввести его вручную.
  - Для prod — `prevent_destroy` в коде + отдельные учётные данные.
- **Дрейф:** сначала понять причину (ручное изменение?), затем `import`/исправление кода; не «затирать» apply-ем вслепую.

## 5. Vault / публикация знаний

### Конфликт
- Добавлять **конкретные файлы** (`git add <file>`), не `git add .`.
- Pre-commit hook с `gitleaks` — blocking.

### Индекс Smart Connections сломан
- Убедиться, что `.smart-env/` производный и не отслеживается git (проверить в `.gitignore`), затем удалять.

### Публикация (default-deny)
- Публикуется только заметка с явной пометкой `publish: true` в frontmatter.
- CI-проверка: секреты, персональные данные, внешние ссылки на приватное.
- Публичный сайт собирается из **экспорта** (отдельный репозиторий `polymath-os-garden`), не из самого vault.
- Отрицательный тест: заметка без пометки с «ловушкой-строкой» не должна появиться в собранном сайте.

### ⛔ Утечка приватной заметки
- Считать публикацию **необратимой**: git-история сохраняет всё навсегда.
- Шаги:
  1. Убрать с сайта и из кэшей CDN.
  2. Ротировать **всё упомянутое в заметке** (секреты, токены, имена, адреса).
  3. Оценить обязанность уведомления (GDPR, regulation, contract).
  4. Переписывать историю git **только как дополнение**, а не замену ротации.

## 6. Агенты и ИИ

- **Регрессия по промпту:** `git revert` через PR + eval-gate (promptfoo regression). **Не** `git checkout` файлов в рабочее дерево без коммита и ревью.
- **Скачок стоимости:** проверить cache-hit-ratio (Langfuse per-agent metric), лимиты, зацикливание инструментов; включить жёсткий лимит бюджета.
- **Агент не получает права шире, чем у человека-владельца задачи** (PID=1).
- **Multi-agent policy:** исследование — параллельные агенты; исполнение с побочными эффектами — single executor + детерминированный независимый проверяющий (тесты/схемы/readback состояния, не второй LLM).

## 7. Секреты

### ⛔ Утечка/подозрение
1. Немедленно отозвать (`gh api -X DELETE /repos/USER/REPO/actions/secrets/NAME`, AWS IAM rotate, etc.).
2. Выпустить новые.
3. Проверить журналы использования за окно экспозиции.
4. Записать, какие системы затронуты.

### Потеря доступа к менеджеру паролей / age-ключу
- Восстановление из **офлайн-копии**, хранящейся отдельно (не в той же системе).
- Раз в квартал — учение «открыть секрет с чистой машины».

### Ротация
- **По классам секретов**, не по календарю.
- Приоритет — короткоживущие учётные данные (OIDC trust между CI и облаком).
- Компрометация предполагается при **индикаторе** (утечка, смена людей/устройств, security advisory), а не по календарю.
- Long-lived credentials (age-key, PGP) — quarterly rotation только как backup, primary через OIDC.

## 8. Доступность человека (соло-режим)

- Alerts не должны зависеть от одного канала: **два канала** (email + Telegram, Telegram + SMS) + heartbeat / dead-man switch («тишина» — тоже сигнал).
- Определить заранее, что система делает без человека:
  - **Безопасная деградация** (отключить функцию флагом).
  - **Никаких необратимых действий** без подтверждения.
- Назначить **доверенное лицо** для критических сбоев; хранить инструкцию доступа отдельно (не в той же системе).
- Backup & DR table — в §10.

---

## 9. Недоступность поставщика (GitHub / облако)

- **Суверенное ядро** (git, markdown, SQLite, age, Nix) должно читаться и собираться локально — клон репо, локальный кэш зависимостей.
- **Арендуемые сервисы** — заменяемы по контракту. Определить replacement для каждого (см. `docs/adr/0002-sovereignty-registry.md`).
- Определить, какие операции откладываются в очередь, а какие запрещены без подтверждения (платежи, отправка сообщений — только после подтверждённого результата).
- **Учение выхода** (раз в квартал): отключить один сервис, показать, что ядро и данные работают, записать время восстановления.

## 10. Бэкапы и восстановление

| Что | RPO | RTO | Проверка |
|---|---|---|---|
| Код/репозиторий | real-time (git push) | задать (target: ≤30 min) | Quarterly: `git clone` на чистую VM, запись времени |
| Vault | 10 min (auto-backup) | задать (target: ≤15 min) | Quarterly: `git clone vault` → открыть в Foam/`less` |
| БД | задать (WAL/PITR, target: ≤5 min) | задать (target: ≤1 h) | Quarterly: восстановление на чистую машину, сверка данных |
| Секреты | — | задать (target: ≤30 min) | Quarterly: открыть секрет с чистой машины из офлайн-копии |

**Значения RPO/RTO — решение владельца; пустая ячейка = невыполнимая гарантия.** Бэкап считается существующим только после успешного восстановления.

Ключи восстановления хранить **отдельно от основного** (не в той же системе/облаке).

## 11. Запись инцидента (связь с SINGULYAR EIR)

Инцидент = `Intent` (что нужно восстановить, ограничения) + `Evidence` (что проверено). Это модель из ядра SINGULYAR EIR (`runtime/docs/TECHNICAL_SPEC.md`).

- **Закрытие** допустимо, когда проверка результата пройдена (не когда команда вернула 0).
- Затем **классификация**:
  - дефект кода → регрессионный тест (в CI)
  - ошибка контракта → правка спецификации (`runtime/schemas/`)
  - внешний сбой → ретрай/резерв
  - единичное событие → без изменения архитектуры
- **Постмортем** — артефакт в git (issue с меткой `incident` + `postmortem`), не «в голове».
