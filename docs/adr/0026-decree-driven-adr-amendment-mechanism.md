# ADR-0026 — Decree-Driven ADR Amendment Mechanism

**Date:** 2026-10-17
**Status:** Accepted
**Tags:** meta, decree, adr, v3.12.0
**Deciders:** @USER
**Supersedes:** None (implements ADR-0016 — Self-Rewriting ADR Mechanism)
**Closes:** ADR-0016 (target-for-v1.0 → fully implemented v3.12.0)

## Context

ADR-0016 specifies the **meta-process** for ADRs — lifecycle
(Proposed → Accepted → Deprecated → Superseded by YYYY), how to add,
how to amend, how this very ADR can itself be amended. But ADR-0016
is descriptive, not operational: it doesn't provide an automation
mechanism.

Per ADR-0021 (Decree as Supreme Law), the human's decrees are above
ADRs. So decrees should drive ADR operations:
- "create ADR-0027 about cell65-llm integration" → ADR-0027 generated
- "amend ADR-0016 to require two-party review" → amendment recorded
- "supersede ADR-0008 with ADR-0028" → ADR-0008 marked Superseded
- "deprecate ADR-0011" → ADR-0011 marked Deprecated

This ADR implements the decree-driven automation for ADR-0016's
meta-process, closing ADR-0016's "target-for-v1.0" status.

## Decision

### 1. New decree category: `amendment`

Existing categories (per `runtime/src/decree_log.py`):
- `law`, `prohibition`, `permission`, `observation`, `directive`

Add: `amendment` — decrees that drive ADR operations. These decrees
are NOT checked by `check_compliance()` (only `law` + `prohibition`
are enforced there). Instead, they are processed by `AdrAmender`.

### 2. Decree patterns recognized

```text
"create ADR-NNNN about <topic>"
"amend ADR-XXXX to <change_description>"
"supersede ADR-XXXX with ADR-YYYY"
"deprecate ADR-XXXX"
```

### 3. AdrAmender class

`runtime/src/adr_amender.py` — `AdrAmender` class:

- `process(decree)` — parse the decree text, identify operation, apply
- `create_adr(adr_number, topic, decree_seq)` — generate new ADR from template
- `amend_adr(target_adr, change_description, decree_seq)` — append amendment section
- `supersede_adr(old_adr, new_adr, decree_seq)` — mark old as Superseded by new
- `deprecate_adr(target_adr, decree_seq)` — mark as Deprecated

### 4. Amendment log

Per ADR-0016 §3, "ADRs are immutable once Accepted". We DON'T modify
the original ADR file. Instead, we maintain `docs/adr/amendments.log`
with append-only entries:

```text
[2026-10-17T08:00:00Z] Decree #8 (amendment): amend ADR-0016 to require two-party review for any new ADR
[2026-10-17T08:05:00Z] Decree #9 (amendment): supersede ADR-0008 with ADR-0027
[2026-10-17T08:10:00Z] Decree #10 (amendment): deprecate ADR-0011
```

This preserves the immutability invariant — original ADRs untouched,
amendments visible in a separate auditable log.

### 5. Amendment ADR generation (optional, per ADR-0016 §3)

When a decree says `"supersede ADR-XXXX with ADR-YYYY"`, the AdrAmender
generates a NEW ADR file at `docs/adr/YYYY-<auto-slug>.md` with:

```markdown
# ADR-YYYY — <auto-generated title from decree>

**Date:** <decree timestamp>
**Status:** Proposed (awaiting human review)
**Supersedes:** ADR-XXXX
**Generated by:** AdrAmender from Decree #N

## Context

<auto-generated context describing the supersession>

## Decision

<decree text as the Decision>

## Consequences

- This ADR was auto-generated from Decree #N
- Human should review and amend before marking Accepted
- ADR-XXXX is now marked "Superseded by ADR-YYYY" in amendments.log
```

Generated ADRs start as `Proposed` — human reviews and marks `Accepted`
after amendment. The decree's authority is recorded but the human's
explicit `Accepted` stamp is still required for enforcement.

## Consequences

**Positive:**
- **Closes ADR-0016** (target-for-v1.0 → fully implemented v3.12.0)
- **Decrees now drive meta-architecture** — the human's word modifies
  the architectural rules, not just runtime behavior
- **Audit trail** — every amendment recorded in `amendments.log`
  with decree reference + timestamp
- **Backward compatible** — ADR-0016's existing process still works
  (manual ADR creation by hand); AdrAmender is opt-in via decree
- **СИНГУЛЯР extension** — decree authority now extends beyond
  runtime (Intent blocking) into architecture (ADR changes)

**Negative:**
- Adds new file `docs/adr/amendments.log` — must be tracked in CI
- Risk of decree-driven ADR spam (mitigated by requiring human
  `Accepted` stamp before enforcement)
- The "what is a meta-change" boundary (per ADR-0016 §Consequences)
  remains fuzzy — AdrAmender treats ALL amendment decrees the same

**Neutral:**
- `amendment` decrees are NOT enforced by `check_compliance()` —
  they're processed separately by `AdrAmender`. This is by design:
  amendment decrees are about ADR changes, not Intent blocking.

## Verification

- `runtime/tests/test_adr_amender.py` — 8+ tests for each decree pattern
- `make verify` check 05 (AUDIT_RESPONSE cross-references all ADRs)
  still passes — ADR-0026 added to AUDIT_RESPONSE.md
- The amendments.log file format is line-based, append-only, hash-chainable
  in future (v3.13.0 candidate)

## Alternatives considered

1. **Modify original ADR file in-place** — rejected: violates ADR-0016
   §3 immutability invariant.
2. **Use git commits as the amendment log** — rejected: git history
   is hard to programmatically query; amendments.log is plain text,
   queryable.
3. **Make AdrAmender auto-mark new ADRs as `Accepted`** — rejected:
   the human's explicit `Accepted` stamp is the governance gate.
   Auto-acceptance would bypass human review.
4. **Use a separate database for amendments** — rejected: text log
   is simpler, grep-able, diff-able in git. SQLite would be overkill
   for ~100 entries over project lifetime.

## Self-reference

This ADR itself can be amended by a future decree. The amendment
would be recorded in `amendments.log`:

```text
[<timestamp>] Decree #N (amendment): amend ADR-0026 to require
  three-party review (instead of two-party) for AdrAmender-generated
  ADRs
```

The original ADR-0026 file remains immutable; the amendment is
visible in the log. This is the recursive fixed point of ADR-0016
made operational.
