# Аудит и ревизия: Polymath OS (отчёт + RUNBOOK) и наш прототип v0.2

Дата: 2026-10-16. Метод: чтение двух приложенных документов (`Polymath-OS-Report.pdf`, `RUNBOOK.md`), сверка с практиками 2025–2026 (см. `RESEARCH.md`), самопроверка пакета v0.2 (код прочитан, тесты запущены, затем применён мутационный контроль).
Формат каждого замечания: **что не так → почему важно → альтернатива → как проверить**. Критика направлена на тексты, а не на цели автора.

Степень уверенности: **[док]** — следует прямо из приложенного текста; **[вывод]** — инженерное суждение; **[проверить]** — зависит от версии/окружения, нужно сверить с первоисточником.

## A. Отчёт Polymath OS

### A1. Этика «LFS» против фактического стека [док] — серьёзное
Тезис 3 объявляет: никаких предсобранных бинарников и внешней зависимости от чужих корпоративных сборок. Стек же целиком состоит из арендованного или чужого: GitHub (CI, репозиторий, Pages), Sentry, 1Password, OpenRouter, BetterStack, Hetzner/Cloudflare, публичная инфраструктура Sigstore, Obsidian (закрытый код).
**Почему важно:** документ называет любую внешнюю зависимость «институциональным захватом», но сам строится на них; принцип невыполним и потому перестаёт управлять решениями.
**Альтернатива — реестр суверенности зависимостей.** Для каждой зависимости: чем заменить, стоимость выхода, можно ли вынести данные в открытом формате. Два яруса: *суверенное ядро* (git, markdown, SQLite, age, Nix — работает без сети и без аккаунтов) и *арендуемые сервисы* (заменяемы по контракту).
**Проверка:** ежеквартальное «учение выхода»: отключить один сервис, показать, что ядро и данные работают, записать время восстановления.

### A2. Арифметика дорожной карты [док]
«4 фазы × ~22 дня», но в таблице 7 / 14 / 39 / 30 дней (дни 1–7, 8–21, 22–60, 61–90).
**Альтернатива:** либо честные длительности фаз, либо переименовать «~22 дня» в «ориентир 90 дней» и поставить к каждой фазе условие выхода (gate) вместо календарной длины. Gates уже есть в отчёте — оставить их главными.

### A3. Уровень SLSA [док] [проверить]
Критерии приёмки — «SLSA Level 2+», текст паттернов — «Level 3 при правильной настройке». Эти заявления совместимы только при доказательстве изоляции сборщика. По описаниям в открытых источниках Build L2 = подписанное происхождение от хостируемой платформы, L3 = платформа препятствует подделке происхождения самой сборкой; актуальная версия спецификации и состав треков (Build/Source) — сверить на slsa.dev.
**Альтернатива:** целевой уровень v1.0 — Build L2; L3 заявлять только после того, как есть свидетельство об изоляции сборщика. Не писать «2+».
**Проверка:** `cosign verify-attestation` в deploy-шаге + отрицательный тест (артефакт без аттестации не деплоится).

### A4. «Self-rollback ≤ 60 сек» [док] [вывод] — серьёзное
Откат приложения (`helm rollback`) не откатывает миграции схемы, внешние побочные эффекты и данные. Метрика 60 сек описывает только самый простой кусок. RUNBOOK при этом допускает 30 минут до решения о откате для P1.
**Альтернатива:** три раздельные цели: (1) откат кода — время; (2) безопасные миграции по схеме expand/contract (откат кода возможен без отката данных); (3) восстановление данных — RPO/RTO с измеренным учением.
**Проверка:** учение «восстановить БД на чистую машину», время и потерянное окно записываются как артефакт.

### A5. Шесть «self-*» свойств — это заявления, а не измерения [док]
Каждое из них нужно переформулировать до гарантии, которую можно опровергнуть:

| Заявление | Что реально гарантирует | Свидетельство, которое требуется |
|---|---|---|
| self-audit | CI проверяет то, что в него включили | карта рисков → проверки; отрицательные тесты (внесённый дефект должен краснить CI) |
| self-publish | деплой по правилам | allowlist публикации + проверка итогового состава (см. A9) |
| self-bootstrap | скрипт запускается | запуск на чистой VM, время и версии записаны |
| self-evidence | документы лежат в git | трассировка «утверждение → тест/запуск» (документы не подтверждают друг друга по кругу) |
| self-verify | подпись артефакта проверена | `verify` на deploy + отрицательный тест |
| self-rollback | откат выполнен | учение + проверка состояния после отката |

### A6. Слоган вместо политики секретов [док]
«Секрет, не меняющийся за 90 дней, = скомпрометирован» — риторика. RUNBOOK при этом ротирует только age-ключ раз в квартал.
**Альтернатива:** ротация по классам секретов; приоритет короткоживущих учётных данных (OIDC); компрометация предполагается при индикаторе (утечка, смена людей/устройств), а не по календарю.

### A7. Multi-agent: проектирование против исполнения [док]
Отчёт цитирует «сначала один агент», методология же использовала четырёх параллельных агентов. Это совместимо, если явно разделить: *исследование* — параллельные агенты; *исполнение с побочными эффектами* — один исполнитель + детерминированный независимый проверяющий. Проверяющий — не второй LLM, а тесты/схемы/readback состояния (как в EIR).

### A8. Актуальность: MCP [док] [проверить]
Отчёт фиксирует передачу MCP в Linux Foundation (дек. 2025) и протокол A2A. По вторичным источникам действующая ревизия спецификации MCP — 2026-07-28 (stateless-ядро, убран initialize-handshake), а семантические соглашения OpenTelemetry для GenAI на момент проверки не стабильны. Отчёт этого не отражает.
**Альтернатива:** держать MCP за тонким внутренним адаптером (в EIR это и есть `Capability` + `Adapter`), закреплять версию, планировать миграции.

### A9. Self-publish из одного репозитория с приватной базой знаний [вывод] — серьёзное
Vault коммитится каждые 10 минут в репозиторий, а «Quartz публикует подмножество» — но механизм выбора подмножества не описан. Ошибка в фильтре = публикация приватных заметок; git-история сохраняет всё навсегда.
**Альтернатива:** default-deny: публикуется только заметка с явной пометкой `publish: true` и прошедшая CI-проверку (секреты, персональные данные, внешние ссылки на приватное). Публичный сайт собирается из *экспорта* (отдельный репозиторий), а не из самого vault.
**Проверка:** отрицательный тест — заметка без пометки с «ловушкой-строкой» не должна появиться в собранном сайте.

### A10. Метрики приёмки как суррогаты [вывод]
Покрытие 80% не говорит, проверены ли критические ветки; «100% сервисов с OTel» не говорит, что трассы полезны; «make destroy ≤ 5 мин» не определяет окружение.
**Альтернатива:** метрика привязана к риску и способу измерения. Для критичных модулей — мутационный контроль. Реальный пример из этого пакета: после 35 зелёных тестов подмена «нечитаемое состояние → UNKNOWN» на «→ CONFIRMED» их не провалила; тест добавлен только после мутации (см. `LIMITATIONS.md`).

### A11. Мелкое [док]
- «Не ставим Docker Desktop», но `act`, devcontainer и Testcontainers требуют контейнерного рантайма — указать, какой (colima/podman) и зафиксировать в ADR.
- PID=1 как метафора допустима; технических требований из неё выводить нельзя (права, изоляция сессий, переносимость) — они должны быть записаны отдельно.

## B. RUNBOOK.md

| № | Что | Риск | Альтернатива |
|---|---|---|---|
| R1 | `tofu force-unlock` без проверки, что `apply` не идёт | порча state | перед: найти владельца блокировки и процесс, снять копию state, `tofu plan`; только с человеческим подтверждением |
| R2 | `tofu destroy # ОСТОРОЖНО: только non-prod` — защита комментарием | уничтожение prod | скрипт-обёртка проверяет имя окружения, `prevent_destroy` для критичных ресурсов, отдельные учётные данные для prod |
| R3 | `git checkout <commit> -- tooling/agents/<name>/` | изменение рабочего дерева без коммита и ревью | `git revert` через PR + прогон promptfoo как gate |
| R4 | `helm rollback` / `argocd app rollback` как универсальное лекарство | не откатывает миграции/внешние эффекты; [проверить] Argo CD отказывает в rollback при включённой автосинхронизации | дерево решений: коррелирует ли сбой с релизом? затронуты ли данные? → откат / fix-forward / failover / заморозка записи |
| R5 | `git add .` при разрешении конфликтов vault | попадание лишнего (секреты, чужие файлы) в коммит | добавлять конкретные файлы; pre-commit gitleaks |
| R6 | Соло on-call: alerts на e-mail/Telegram | человек спит = инцидента нет | heartbeat/dead-man switch, второй канал, явное «режим недоступности» |
| R7 | `curl /health` как проверка | health ≠ рабочий пользовательский путь | синтетическая проба ключевого сценария |
| R8 | Бэкапы: восстановление раз в квартал, RPO/RTO не заданы | непроверенный бэкап = его нет | RPO/RTO в таблице, учение с записью времени, хранение ключей восстановления отдельно от основного |
| R9 | Нет runbook-ов: утечка секрета, утечка через публикацию vault, потеря 1Password/age-ключа, сбой supply-chain проверки, недоступность GitHub, потеря ноутбука | самые болезненные сценарии не описаны | см. `RUNBOOK_HARDENED.md` |
| R10 | Процедуры не имеют предусловий, проверки результата и «что если сама процедура упала» | | шаблон процедуры в `RUNBOOK_HARDENED.md` |
| R11 | Инцидент не оставляет проверяемого следа (хронология ведётся «в голове»/issue) | postmortem по памяти | запись инцидента как intent + evidence (журнал EIR), закрытие только после проверки результата |

Каждое «выполнено» в RUNBOOK должно подтверждаться проверкой состояния, а не отсутствием ошибки команды — это тот же принцип, что в ядре EIR (адаптер сказал «ок» ≠ результат подтверждён).

## D. Что в итоге изменено и почему именно так

1. Центральное свойство сформулировано проверяемо: «сохранение намерения при замене исполнителя + никаких заявлений об успехе без подтверждённого конечного состояния + честный UNKNOWN». «Эмерджентность» остаётся *гипотезой*; что именно докажет её — `EXPERIMENT_PLAN.md`.
2. Из отчёта Polymath OS взято то, что выдерживает проверку: репозиторий как источник истины, markdown-first, eval в CI, ADR, обратимость. Заменено: самоназванные «self-*» → условия с тестом (A5).
3. Выстроена лестница абляции B0→B3→EIR, где каждое звено убирает конкретный класс отказа (`EXPERIMENT_RESULTS.md`), и тест проверяет, что каждое звено несущее.
