# Redaction Audit — runtime/docs/REDACTION_AUDIT.md

Date: 2026-10-16. Performed as part of Gate-2 (ADR-0010 — mutation testing on critical
paths). Audits the HMAC fingerprint redaction in the SINGULYAR EIR ledger against
the SHA256SUMS.txt file (which is generated by `scripts/check.py`).

## What SHA256SUMS.txt actually contains

`runtime/SHA256SUMS.txt` is a list of file hashes (CycloneDX-style supply-chain
provenance), generated by `scripts/check.py` from a real test run:

```
0baadc0891d8def2fa2573e04fd5918d2ec509ecb73cbd5b8e324c92e58e3e71  CHANGELOG.md
0fe23df83b4f1e898808fe9670613182d90dd8314a660c05bc725223db1fdb43  README.md
...
```

It contains NO payload values, NO evidence records, NO ledger event content. The
SHA-256 of each file is just a content digest for reproducibility verification —
not a redaction mechanism.

## What the LEDGER contains (the actual redaction surface)

Per ADR-009 and `runtime/src/singulyar_runtime.py` (`_log_evidence` method), the
ledger stores HMAC fingerprints of `expected` and `observed` payloads, plus the
sorted field names (`payload_keys`), NEVER the values themselves:

```python
def _log_evidence(self, kind, ev):
    payload = {
        "kind": kind,
        "intent_id": ev.intent_id,
        "verifier": ev.verifier,
        "verdict": str(ev.verdict),
        "observed_status": str(ev.observed_status),
        "expected_fp": hmac.new(self.redaction_key, _canonical(ev.expected), hashlib.sha256).hexdigest(),
        "observed_fp": hmac.new(self.redaction_key, _canonical(ev.observed), hashlib.sha256).hexdigest() if ev.observed is not None else "",
        "note": ev.note,
    }
    self.ledger.append("EVIDENCE", payload)
```

The literal test `test_ledger_never_contains_payload_values` puts the string
`"S3CRET-PAYLOAD-VALUE"` into a payload and asserts the literal string never
appears in `ledger.events`.

## The vulnerability: low-entropy values are brute-forceable

The HMAC fingerprint itself is a SHA-256 truncated hash. If an attacker has:
1. The `redaction_key` (per LIMITATIONS.md item 4, key custody is operator's job, not kernel's)
2. A captured ledger event with `expected_fp` / `observed_fp`

Then for **low-entropy values** (e.g. `{"ok": true}`, `"yes"`, `"1"`, `[]`, `null`),
the attacker can recover the original value by trying common candidates against
the same HMAC function and matching fingerprints. This is a small-preimage-space
attack — completes in seconds on a laptop.

For **high-entropy values** (UUIDs, random tokens, long structured data), the
attack is infeasible (256-bit search space).

## Mitigation status

This is **documented** in `runtime/docs/LIMITATIONS.md` item 4:

> "HMAC fingerprints protected by `redaction_key` — not stored, not rotated
>  by the kernel; wrong key → `ContractError` on recover/resume"

But the brute-forceability of low-entropy values is **not explicitly called out**
there. This audit recommends adding to LIMITATIONS.md item 4 the following:

```
Residual: low-entropy values (e.g. {"ok": true}, "1", "yes") have small
preimage space under HMAC-SHA-256; an attacker with redaction_key + fingerprint
can recover the value by dictionary attack in seconds. Mitigation in v0.4:
add per-entry random salt (16 bytes) to HMAC input — `expected_fp =
HMAC(key, salt + canonical(expected))`, store `salt` alongside the fingerprint.
This raises the preimage space per entry to 2^128, even for low-entropy values.
```

## What was actually audited

- ✅ `SHA256SUMS.txt` — no payload values, only file hashes (safe)
- ✅ `evidence.schema.json` — `expected_fp` and `observed_fp` are HMAC hex strings, no
  salt field, no value field
- ✅ `singulyar_runtime.py:_log_evidence` — does NOT log payload values, only fingerprints
  + field names
- ✅ `test_ledger_never_contains_payload_values` — regression test confirms no literal
  payload value reaches the ledger
- ⚠️ HMAC fingerprints for low-entropy values are brute-forceable with key+fp access —
  residual vulnerability, mitigated in v0.4 with per-entry salt
- ✅ Test `test_wrong_redaction_key_cannot_bind_to_existing_task` — wrong key raises
  ContractError (fail-closed)

## Verdict

The redaction design is sound for the threat model where the `redaction_key` is
operator-controlled and never leaks. The residual risk — low-entropy value
recovery given key+fp access — is acceptable for the current v0.3 prototype
(single-writer, no real network, no real credentials) and **will be closed in
v0.4** with per-entry salt.
