# RUNBOOK (усиленная версия) — альтернатива исходному RUNBOOK.md

Принципы: (1) у каждой процедуры есть предусловия, предпросмотр, проверка результата и план «если процедура сама упала»; (2) «выполнено» = состояние подтверждено проверкой, а не команда вернула 0; (3) необратимое действие требует явного подтверждения человека; (4) неизвестное состояние — это состояние (`UNKNOWN`), его не «додумывают».

Это предложение, а не проверенный в вашей среде документ: команды требуют пробного прогона в тестовом окружении. Отмечено **[проверить]**, где поведение зависит от версии.

## 0. Шаблон процедуры
```
ПРЕДУСЛОВИЯ   что должно быть верно до начала (и как проверить)
ПРЕДПРОСМОТР  режим «посмотреть, не меняя» (plan / --dry-run / diff)
ДЕЙСТВИЕ      минимальный шаг; необратимое отмечено ⛔ и требует подтверждения
ПРОВЕРКА      наблюдаемый признак успеха (не «команда завершилась»)
ЕСЛИ УПАЛО    что делать, если сама процедура сорвалась; фиксировать UNKNOWN
СЛЕД          запись: время, кто, что проверено, ссылка на артефакты
```

## 1. Триаж инцидента (вместо «P0 → откат немедленно»)
1. Что сломано и у кого? Есть ли риск потери/порчи данных? Если да — **сначала остановить запись**, затем думать.
2. Коррелирует ли сбой с релизом (время, диф, флаги)? Если нет — откат не поможет.
3. Выбор: **откат** (релиз виноват, схема совместима), **fix-forward** (откат невозможен: миграция необратима), **failover** (виновата зависимость), **деградация** (отключить функцию флагом).
4. Решение и обоснование записать до исполнения (одна строка). 
5. Проверка — синтетическая проба ключевого пользовательского пути, не только `/health`.

## 2. Откат релиза
- ПРЕДУСЛОВИЯ: последняя зелёная ревизия определена; миграции схемы по схеме expand/contract (старый код работает на новой схеме) — иначе откат кода запрещён, идти fix-forward.
- ПРЕДПРОСМОТР: `helm history` / `argocd app history`; сравнить диф ревизий.
- ДЕЙСТВИЕ: `helm rollback <release> <rev>`; **[проверить]** Argo CD может не допускать rollback при включённой автосинхронизации — временно отключить синхронизацию осознанно и вернуть после.
- ПРОВЕРКА: проба пути + метрика ошибок возвращается к фону.
- ЕСЛИ УПАЛО: зафиксировать UNKNOWN, заморозить деплои, эскалация (п. 8).

## 3. CI красный на main
Воспроизвести локально (`act`); если локально зелёно — проблема среды (кэш, образ раннера, закреплённые версии). Фикс — отдельная ветка + PR. Не отключать проверку, чтобы «позеленело»; временное исключение оформляется ADR с датой снятия.

## 4. IaC (OpenTofu)
- Любое действие начинается с `tofu plan` и сохранения копии state.
- `force-unlock`: ПРЕДУСЛОВИЯ — подтверждено, что процесс `apply` не выполняется (проверить владельца блокировки, CI-джобы, локальные процессы); только с подтверждением человека; ПРОВЕРКА — `tofu plan` без неожиданных изменений.
- `destroy`: ⛔ только скриптом-обёрткой, которая проверяет имя окружения и требует ввести его вручную; для prod — `prevent_destroy` и отдельные учётные данные.
- Дрейф: сначала понять причину (ручное изменение?), затем `import`/исправление кода; не «затирать» apply-ем вслепую.

## 5. Vault / публикация знаний
- Конфликт: добавлять конкретные файлы (`git add <file>`), не `git add .`; pre-commit с gitleaks.
- Индекс Smart Connections: убедиться, что `.smart-env/` производный и не отслеживается git, затем удалять.
- Публикация: default-deny (`publish: true` + CI-проверка); публичный сайт из экспорта.
- **Утечка приватной заметки:** ⛔ считать публикацию необратимой: убрать с сайта и из кэшей CDN, ротировать всё упомянутое в заметке, оценить обязанность уведомления, переписывать историю git только как дополнение, а не замену ротации.

## 6. Агенты и ИИ
Регрессия по промпту: `git revert` через PR и eval-gate (не `git checkout` файлов в рабочем дереве). Скачок стоимости: проверить cache-hit, лимиты, зацикливание инструментов; включить жёсткий лимит бюджета. Агент не получает права шире, чем у человека-владельца задачи.

## 7. Секреты
- **Утечка/подозрение:** ⛔ немедленно отозвать, затем выпустить новые; проверить журналы использования за окно экспозиции; записать, какие системы затронуты.
- Потеря доступа к менеджеру паролей/ключу age: восстановление из офлайн-копии, хранящейся отдельно; раз в квартал — учение «открыть секрет с чистой машины».
- Ротация: по классам секретов, предпочтительны короткоживущие учётные данные (OIDC).

## 8. Доступность человека (соло-режим)
Alerts не должны зависеть от одного канала: два канала + heartbeat/dead-man switch («тишина» — тоже сигнал). Определить заранее, что система делает без человека: безопасная деградация, никаких необратимых действий без подтверждения. Назначить доверенное лицо для критических сбоев и хранить инструкцию доступа отдельно.

## 9. Недоступность поставщика (GitHub/облако)
Ядро и данные должны читаться и собираться локально (клон репозитория, markdown, локальный кэш зависимостей). Определить, какие операции откладываются в очередь, а какие запрещены, пока нет подтверждения (платежи, отправка сообщений — только после подтверждённого результата).

## 10. Бэкапы и восстановление
| Что | RPO | RTO | Проверка |
|---|---|---|---|
| код/репозиторий | задать | задать | клон на чистую VM, запись времени |
| vault | задать | задать | открыть без Obsidian (Foam/`less`) |
| БД | задать (WAL/PITR) | задать | восстановление на чистую машину, сверка данных |
| секреты | — | задать | открыть секрет с чистой машины |
Значения RPO/RTO — решение владельца; пустая ячейка = невыполнимая гарантия. Бэкап считается существующим только после успешного восстановления.

## 11. Запись инцидента (связь с EIR)
Инцидент = intent (что нужно восстановить, ограничения) + evidence (что проверено). Закрытие допустимо, когда проверка результата пройдена; затем классификация: дефект кода → регрессионный тест; ошибка контракта → правка спецификации; внешний сбой → ретрай/резерв; единичное событие → без изменения архитектуры.
